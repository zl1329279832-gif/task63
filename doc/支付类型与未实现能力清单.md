# 支付类型与未实现能力清单

> 基准代码：`ShangpinOrderController.java`（`com.controller.ShangpinOrderController`）
>
> 本文档梳理当前支付类型的实现现状，并列出代码中预留但未实现的能力。

---

## 1. 支付类型定义

字段 `shangpin_order_payment_types`（`ShangpinOrderEntity.shangpinOrderPaymentTypes`），整型，存储于字典表 `dictionary`。

| 类型码 | 含义 | 实现状态 |
|--------|------|----------|
| **1** | 余额支付 | **已实现** — 唯一可用的支付方式 |
| **2** | 积分支付 | **未实现** — 所有入口均显式拒绝 |

---

## 2. 余额支付（类型 1）现状

### 2.1 下单流程

- **`add()`（单品下单）**：强制将 `shangpinOrderPaymentTypes` 覆盖为 `1`，无论客户端传入何值（第 371 行）。
- **`order()`（多品下单）**：使用客户端传入的 `shangpinOrderPaymentTypes` 值，仅拒绝值为 `2` 的情况。**[风险]** 若客户端传入 `1` 以外的其他值（如 3、0、null），该值会被原样存入数据库。

### 2.2 计价逻辑

```
实付价格 = shangpin.shangpinNewMoney（商品现价） × buyNumber（购买数量）
```

- 使用 `BigDecimal` 进行乘法运算，结果转为 `double` 存入 `shangpinOrderTruePrice`。
- **不使用原价（`shangpinOldMoney`）**，仅使用现价。
- 无折扣、优惠券、满减等机制。

### 2.3 余额变动

| 场景 | 用户余额 (`yonghu.newMoney`) | 店家余额 (`shangjia.newMoney`) |
|------|------------------------------|-------------------------------|
| 下单 | 减少 `totalPrice` | 增加 `totalPrice` |
| 退款 | 增加 `refundAmount` | 减少 `refundAmount` |

- 余额使用 `Double` 类型（`decimal(10,2)`），运算通过 `BigDecimal` 中转以减少浮点误差。
- **[风险]** 最终存储仍为 `double`，长期高频交易可能出现精度累积偏差。

### 2.4 余额校验

| 校验点 | 位置 | 逻辑 |
|--------|------|------|
| 下单前用户余额充足 | `add()` / `order()` | `余额 - 总价 >= 0` |
| 退款前店家余额充足 | `refund()` | `店家余额 >= 退款金额` |
| 用户余额非 null | `add()` / `order()` / `refund()` | `yonghu.newMoney != null` |

**[风险]** 不校验用户余额和店家余额是否为负值（仅校验非 null 和是否够用）。如果余额因外部原因变为负数，系统不会阻止继续使用。

## 3. 积分支付（类型 2）—— 未实现

### 3.1 拦截位置

| 方法 | 拦截代码 | 错误信息 |
|------|----------|----------|
| `add()` | `if(shangpinOrderPaymentTypes != null && shangpinOrderPaymentTypes == 2)` | "暂不支持积分支付" |
| `order()` | 同上 | "暂不支持积分支付" |
| `refund()` | `if(shangpinOrderPaymentTypes != null && shangpinOrderPaymentTypes == 2)` | "暂不支持积分支付退款" |

### 3.2 缺失的基础设施

若要实现积分支付，以下基础设施当前完全不存在：

| 缺失项 | 说明 |
|--------|------|
| 用户积分字段 | `YonghuEntity` 中无任何积分相关字段 |
| 积分充值/获取 | 无积分来源逻辑 |
| 积分兑换比率 | 无积分与金额的换算配置 |
| 积分扣减/回滚 | 无积分事务处理逻辑 |
| 店家积分结算 | 积分支付后店家如何收款未定义 |

### 3.3 实现积分支付需要的改动范围（评估）

1. `YonghuEntity` / `yonghu` 表：新增积分字段
2. `ShangpinOrderController.add()` / `order()`：新增积分计价和扣减分支
3. `ShangpinOrderController.refund()`：新增积分退还分支
4. 新增积分充值/消费/查询接口
5. 新增积分兑换比率配置（可能需要新表或系统配置）
6. 店家结算：积分订单的店家收入如何计算

## 5. `shangpinOrderPaymentTypes` 值域安全分析

当前代码仅对值 `2` 做了显式拦截，对其他非预期值无处理：

```
客户端传值 → add()  : 任何值均被覆盖为 1 ✓ 安全
客户端传值 → order(): 仅拒绝 2，其他值原样存入 ✗ 不安全
```

**可能出现的异常值及其影响：**

| 传入值 | `order()` 行为 | `refund()` 行为 |
|--------|----------------|-----------------|
| `1` | 正常 | 正常退款 |
| `2` | 拒绝 | 拒绝 |
| `0` / `3` / `99` | 存入数据库 | 订单状态改为 102（已退款），但 **不执行余额退还**（因为不进入 `if(type==1)` 分支），库存仍然恢复 |
| `null` | 存入 null | 跳过积分检查，跳过余额退款分支，状态改为 102，**不退钱不退积分但恢复库存** |

**[风险]** `order()` 应在入口处校验 `shangpinOrderPaymentTypes` 必须等于 `1`（或与 `add()` 一致强制设为 `1`），否则会产生无法正常退款的"僵尸"支付类型订单。
